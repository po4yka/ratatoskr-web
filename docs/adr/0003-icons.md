# ADR-0003: lucide for icons, itshover where motion earns its place

> Status: Accepted  
> Date: 2026-08-19

## Context

The client arrived with `lucide-react`, which is shadcn's default and what every generated component
imports. [itshover](https://github.com/itshover/itshover) is a set of 263 animated icons distributed
as a shadcn registry, built on `motion/react`.

Two icon sets in one client is normally a smell: two GitHub marks that do not match, twice the
bundle, and a decision to make at every call site. It is worth it only if the second set does
something the first cannot, and only if the rule for choosing is written down.

## Decision

**`lucide-react` is the icon set.** itshover is the exception, used where motion carries something —
feedback on an action, a state that changed, an affordance worth pointing at. Both are registered:
`components.json` keeps `iconLibrary: "lucide"` and adds `@itshover` to `registries`.

Every itshover icon is rendered through `src/components/animated-icon.tsx`, never directly.

## What the wrapper is for

The generated icon source has two properties this repository cannot live with, and neither can be
fixed in place — `src/components/ui/` is regenerated by `shadcn add`, so an edit there is lost.

**It drops every prop but four.** The component destructures `size`, `color`, `strokeWidth` and
`className`. `aria-hidden`, `aria-label`, `role` and `data-*` cannot reach the `svg`. Without a
wrapper there is no way to mark an icon decorative, name a meaningful one, or give the shadcn Button
the `data-icon="inline-start"` it needs for spacing.

**Its animation is invisible to `MotionConfig`.** The icons animate through motion's imperative
`animate()` from `useAnimate`. The documentation for `reducedMotion="user"` says it disables
transform animations for `motion` components; measured against these icons, the transform is still
applied. `src/components/animated-icon.test.tsx` holds that measurement, and it asserts the unhelpful
behavior on purpose: if a future motion release starts covering the imperative path, the test fails
and the CSS backstop below can be reconsidered.

So reduced motion is enforced in CSS, scoped to `[data-animated-icon]`, where no JavaScript can route
around it. `MotionConfig reducedMotion="user"` stays mounted in `main.tsx` for the declarative motion
we write ourselves. The two cover different paths and neither replaces the other.

## Consequences

- `motion` is now a runtime dependency and ships to the browser. It is the largest thing this client
  carries that is not React, which is the cost side of this decision and the reason the icons are an
  exception rather than the default.
- The registry fetch happens at `shadcn add` time, not at runtime. Nothing in the serving path talks
  to `itshover.com`, so `SECURITY.md`'s no-third-party-host rule is untouched.
- The icons are **Apache-2.0** while this repository is BSD 3-Clause. The repository README of
  itshover says MIT; its `LICENSE` file says Apache-2.0, and the file governs. Apache-2.0 permits
  vendoring and requires the licence and attribution be preserved — `src/components/ui/NOTICE.md`
  records both.
- The animation fires on hover, so a keyboard user never sees it. That is acceptable only while it
  carries no information, which is a rule in `AGENTS.md` rather than something the code enforces.
- shadscan reports `animations-respect-reduced-motion` as passing since the backstop landed, which is
  a check on this decision from outside it.

## Validation

Typecheck, lint, format, unit tests and build pass. `src/components/animated-icon.test.tsx` covers
the decorative and named accessibility contracts, the presence of the backstop in the stylesheet, and
the motion measurement above. shadscan scores 69 with `animations-respect-reduced-motion` passing.

## Follow-up

Revisit if `motion` bundle cost shows up in a measured reader-view budget, or if a keyboard user
turns out to need the state the animation conveys — at which point the state belongs somewhere other
than in an animation.
